# AIRP 依赖锁定与升级政策

**版本**：v1.0  
**生效日期**：2026-09-19  
**关联决策**：总设计案 v4 项 29；项目实现步骤蓝图 阶段 0 任务 3

---

## 一、背景与第一性原理

在酒馆生态与独立叙事应用中，LLM Provider 层是整个应用的地基。参考项目（如梨园、dsh-tavern）的历史血泪经验证明：
1. 第三方 AI SDK / Provider 层的静默更新、破坏性破坏（breaking changes）或内部行为漂移（如流式事件切分变动、Abort 信号截断失效、token 统计格式调整）会导致上层会话崩溃或静默数据损坏；
2. 将 SDK 与应用深耦合或依赖语义版本通配符（如 `^`、`latest`），会导致不同环境下构建产物行为不一致；
3. AIRP 明确将 `@earendil-works/pi-ai` 仅作为 `ModelPort` 适配器（封装在边界之后），绝对禁止其渗透至 Core 领域。

因此，AIRP 执行严格的**全量依赖锁定**与**显式升级门槛**政策。

---

## 二、依赖锁定规范

1. **版本声明收紧**：
   - 生产项目与开发依赖一律使用**固定版本号**（Exact Versioning，如 `"@earendil-works/pi-ai": "0.85.1"`），禁止在 `package.json` 中使用 `^`、`~`、`latest`。
   - `pnpm-lock.yaml` 必须强制纳入版本控制（Git 追踪），并在 CI / 部署环境中必须通过 `pnpm install --frozen-lockfile` 执行安装。

2. **零静默升级（No Auto-Update）**：
   - 禁止任何全自动依赖更新 bot（如 Dependabot、Renovate）对 Provider / Core 相关依赖直接自动合并。
   - 禁止在日常开发、修复 bug 或重构时顺手执行无参数的 `pnpm update`。

3. **干净室与许可证隔离**：
   - 任何引入的新依赖必须符合 PolyForm Noncommercial 1.0.0 兼容许可要求（MIT / Apache 2.0 / BSD / ISC 等宽松开源协议可用；禁止直接引入 AGPL-3.0 传染性源码或未经审核的代码段）。

## 三、ModelPort (pi-ai) 显式升级流程

对 `@earendil-works/pi-ai` 及任何后续 Provider SDK 的升级，必须遵循以下六步闭环流程：

```
[显式升级提案] → [Bump 版本并更新 Lockfile] → [阶段 0 Spikes 冒烟验证] → [Golden Transcript 回归门槛] → [API 契约 Diff 审计] → [准予合并]
```

### 1. 显式升级提案与变更动因
- 必须有明确动因（例如：修复 upstream critical bug、接入新 Provider / 新模型能力、严重安全漏洞修补）。
- 记录当前锁定版本与目标版本（例如：`0.85.1` -> `0.86.0`）。

### 2. 本地单步升级并更新锁文件
- 在独立工作分支中执行明确锁定安装：
  ```bash
  pnpm add --save-exact @earendil-works/pi-ai@<TARGET_VERSION>
  ```
- 确认仅目标包及其合法传递依赖发生变化，生成更新后的 `pnpm-lock.yaml`。

### 3. 基座 Spike 冒烟验证
必须运行阶段 0 的自动化验证套件并全绿通过：
```bash
node spikes/pi-ai-standalone/spike.mjs
node spikes/pi-ai-standalone/probe.mjs
```
必须逐项确认：
- 流式事件（`start` -> `text_delta` -> `text_end` -> `done`）序列与完整性；
- `AbortSignal` 取消传导至底层 HTTP 连接；
- Usage 元数据（尤其是 `cacheRead` / `prompt_tokens_details`）未丢失。

### 4. Golden Transcript 回归门槛（不可动摇门禁）
- 运行 AIRP Core 的 Golden Transcript 测试套件（记录的真实输入与固定预期输出/事件轨迹）。
- 新版本在相同 mock / 录制数据下的事件流产生结果必须与 golden snapshot 100% 保持一致。
- 若事件格式或流式 chunk 拆分发生变化，需确认是否为非功能性格式微调，严禁语义漂移。

### 5. API 契约与出口审计
- 审查新版本对外暴露的 export 方法与类型定义：
  - 是否依然支持 `api/openai-completions`、`api/anthropic-messages`、`api/google-generative-ai` 的 `streamSimple`；
  - 是否引入了不需要的巨型依赖或进程级副作用；
  - 确认依赖树未反向依赖 `pi-coding-agent` 或其他重型运行体。

### 6. 合并交付与记录更新
- 确认所有测试全绿；
- 更新 `NEXT.md` 中的依赖版本记录；
- 提交 PR，由项目主理人签署合并。

---

## 四、应急降级与回退预案

若 `@earendil-works/pi-ai` 发生不可逆的破坏性变更、上游停止维护或与未来 Node / 运行时发生严重冲突：
- **第一备选预案已冻结**：退回自写纯 TS 最小化 OpenAI 兼容层（包含 `fetch` + SSE parser + AbortSignal 传递 + usage 解析，预估 < 250 行代码）。
- ModelPort 的接口隔离保证上层 Core、管家与持久化完全无感，仅需切换 ModelPort 的底层实现。
