## 一、文件清单与职责

本阶段严格在任务书划定的文件边界内实施，未触碰任何禁改目录或文件，未新增任何第三方依赖，严格遵守 ESM、NodeNext 规范及 TypeScript Strict 模式：

1. **`src/runtime/paths.ts`**
   - 职责：AIRP_HOME 环境变量解析（相对路径规范化为绝对路径、缺省回退至 `~/.airp`）、卡片与会话子目录层级生成。
   - 核心安全防线：`assertSafeId()` 严格限制 ID 必须匹配 `^[A-Za-z0-9_-]{1,64}$`，彻底阻断路径穿越攻击（例如 `../evil`、绝对路径等）。
2. **`src/runtime/fs-atomic.ts`**
   - 职责：原子化文件系统操作底座。
   - 核心能力：`ensureDir` 递归建目录、`writeAtomic`（同目录随机后缀临时文件 + `fsync` + 原子 `rename` 覆盖目标）、`writeJsonAtomic`、`readJson` 与 `copyDirectory` 递归复制。
3. **`src/runtime/event-log.ts`**
   - 职责：JSONL append-only 事件日志引擎。
   - 核心能力：
     - Promise 队列串行化并发写入，分配会话内单调递增连续 `seq`（从 1 开始）；
     - 使用 `fs.open(path, 'a')` + `fsync` 确保原子持久化；
     - 崩溃尾行容忍：`readAll` / `readFrom` 自动识别并丢弃被进程中途中断写出的半截 JSON；
     - `repairTail`：截断损坏尾行，返回被截断字节数，使后续追加可无缝继续；
     - `snapshotInterval` 触发回调支持。
4. **`src/runtime/snapshot-store.ts`**
   - 职责：快照 checkpoint 的持久化与容错加载。
   - 核心能力：保存 `snapshots/<seq>.json`（原子写）、升序枚举 `list()`，以及快照损坏自动向历史有效快照回退的 `latest()`。
5. **`src/runtime/migrations.ts`**
   - 职责：版本化卡片目录迁移。
   - 核心能力：自动识别缺失或不同 schemaVersion 的目录，迁移前自动备份至 `backups/<timestamp>/`，执行无损升级（0 -> 1），并在版本一致时保证幂等无备份。
6. **`src/runtime/card-store.ts`**
   - 职责：实现架构层冻结契约 `CardStoreFacade` 的全部方法。
   - 核心能力：卡片生命周期管理、物理隔离独立存储、事件追加分发、快照加速重放、导出/导入无损往返以及版本迁移门面。
7. **`tests/runtime/store/*.test.ts`**
   - `paths.test.ts`：测试路径解析与 ID 穿越防御。
   - `event-log.test.ts`：测试并发 append 连续性与崩溃尾行恢复。
   - `snapshot-store.test.ts`：测试快照保存与损坏自动回退。
   - `card-store.test.ts`：涵盖 200+ 混合随机事件重放一致性、快照加速重放、迁移演练、无损往返、物理隔离与物理遗忘恢复。

## 三、事件重放算法说明

重放函数 `replay(cardId, sessionId): Promise<ReplayResult>` 实现了确定性的内存态重建：

```mermaid
graph TD
    A[开始重放] --> B[SnapshotStore.latest 加载最新有效快照]
    B -->|快照存在| C[以快照为起点: tree, state, summary, seq=snapshot.seq]
    B -->|无快照/快照均损坏| D[空树初始化: rootFloorId=null, branch=main, state={}, summary=null, seq=0]
    C --> E[EventLog.readFrom 从 checkpoint.seq + 1 顺序读取增量事件]
    D --> E2[EventLog.readFrom 从 1 顺序读取完整事件]
    E --> F[顺序应用 applyEventToMemory]
    E2 --> F
    F --> G[产出 ReplayResult: tree, state, summary, lastSeq, replayedEvents, fromCheckpointSeq]
```

**各事件在 `applyEventToMemory` 中的折叠规则**：
1. `session_created`：确保 `activeBranchId = "main"`。
2. `floor_appended`：插入新楼层（`swipes = [content]`，`currentSwipeIndex = 0`，`editHistory = []`），更新根楼层。
3. `floor_swiped`：追加 swipe 到楼层并在当前楼层内容切换为最新 swipe。
4. `floor_edited`：将当前内容记录进 `editHistory`，更新 `content` 与当前 swipe 内容。
5. `branch_switched`：切换当前活跃分支 `activeBranchId`。
6. `rollback`：记录活跃分支最高 `floorIndex` 楼层至 `undoCheckpointFloorId`，物理删除 `forgottenFloorIds` 中的楼层。
7. `undo_rollback`：只依赖事件自带的 `payload.restoredFloors` 自包含数据恢复楼层，校验 `restoredFloorIds` 一致性，清空 `undoCheckpointFloorId`。
8. `state_op`：调用核心领域模型 `applyStateOp(state, op)` 进行原子状态折叠。
9. `summary_updated`：更新当前会话摘要。
10. `run_*` 与 `checkpoint`：作为辅助/元事件安全忽略，不修改楼层树或状态。

## 四、契约缺口说明与修正（Contract Gaps & Revision）

### 历史缺口与错误推论（已判定不成立）
在阶段 2 初次交付时，曾认为：
> "在重放算法内部维护一个增量楼层归档 `floorArchive`……当发生 undo_rollback 时，从 `floorArchive` 中还原完整楼层对象，既完全遵守了冻结的 contracts.ts 定义，又实现了物理遗忘与撤销能力。"

**该推论已被红队验收与探针判定完全不成立**：
因为 `floorArchive` 是重放过程中的单次内存局部状态，一旦系统在 rollback 之后生成了快照（checkpoint），后续重放以该快照为起点，快照树不含被遗忘楼层，重放起点的 `floorArchive` 必然为空，导致快照边界后的 `undo_rollback` 永远无法恢复楼层（数据永久丢失，即缺陷 A）。同时，旧实现用历史全部追加楼层集合求差，导致多次 rollback 后 undo 会过度复活早先已确认遗忘的楼层（缺陷 B）。

### 正确修正方案
架构层在 `contracts.ts` 中将 `UndoRollbackEvent.payload` 扩展为自包含恢复结构：
```typescript
export interface UndoRollbackEvent extends RuntimeEventBase {
  type: "undo_rollback";
  payload: {
    restoredFloorIds: string[];
    restoredFloors: FloorMessage[];
  };
}
```
重放彻底废弃内存 `floorArchive`，`undo_rollback` 事件自包含全部被恢复楼层的完整快照，重放只依赖事件自身，天然保证「跨快照边界恢复」与「全量重放 vs 快照增量重放」的严格一致性。

## 七、红队验收修复记录（任务 A2）

### 1. 缺陷复现与根因分析

#### 缺陷 A：快照边界之后 undo_rollback 完全失效（数据永久丢失）
- **复现步骤**：
  配置 `snapshotInterval = 1`，依次追加 1、2、3 楼；执行 `rollback` 到 1 楼（因 interval=1 触发快照，快照树仅包含 1 楼）；执行 `undoRollback` 并重放。
- **根因**：
  旧版 `replay()` 依赖单次重放的内存局部状态 `floorArchive`。当最新快照在 rollback 之后生成时，重放从该快照之后开始读取事件，`floorArchive` 仅初始化了快照内可见的 1 楼，重放推进到 `undo_rollback` 时找不到 2、3 楼的历史数据，恢复静默失败，数据永久丢失。

#### 缺陷 B：连续两次 rollback 后 undo 会复活"已确认遗忘"的楼层
- **复现步骤**：
  依次追加 1 到 5 楼；先 `rollback` 到 3 楼（遗忘 4、5 楼）；再 `rollback` 到 2 楼（遗忘 3 楼）；执行 `undoRollback`。
- **根因**：
  旧版 `undoRollback()` 使用“历史上所有 `floor_appended` 楼层集合减去当前可见楼层集合”来计算恢复集，混淆了历史所有回退点，导致第二次回退撤销时错误地将第一次回退已永久遗忘的 4、5 楼一并复活。正确语义要求恢复点只对最近一次 rollback 有效，更早的遗忘必须永久保持。

### 2. 修复方案
1. **`undoRollback()` 精确恢复点**：
   在 `undoRollback()` 内部从头扫描完整事件流建立参照状态，精确捕获**最后一次** `rollback` 事件所物理遗忘的楼层完整数据（深拷贝 `FloorMessage`，保留完整 `swipes`、`currentSwipeIndex` 与 `editHistory`），将其装填进 `payload.restoredFloors`。若恢复点已被失效（其后存在追加、swipe 或编辑），或不存在 rollback 事件，严格拒绝并抛错。
2. **`replay()` 自包含重放**：
   `case "undo_rollback"` 直接解构 `ev.payload.restoredFloors` 还原楼层，完全移除 `floorArchive` 内存归档机制；校验 `restoredFloors` 与 `restoredFloorIds` 集合一致性；重置 `undoCheckpointFloorId = null`。
3. **重放不变量测试与回归测试**：
   - 补充 `tests/runtime/store/card-store.test.ts` 中的缺陷 A 与缺陷 B 回归测试；
   - 新增 `tests/runtime/store/invariants.test.ts`，施加 160 条混合高压操作（频繁触发快照、回退、撤销），比对「全量重放」与「小间隔快照 + 增量重放」在 `tree`、`state`、`summary`、`lastSeq` 上的深度完全一致性。

### 3. 探针验证原始证据

#### 修复前探针输出（3/5 通过，A/B 失败）
```text
FAIL  A. 快照边界后 undo_rollback 应恢复全部被遗忘楼层
```
