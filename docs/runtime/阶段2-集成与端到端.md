## 二、真实端口 → allowedOrigins 的接线顺序说明

### 1. 接线陷阱原理
在 `src/runtime/server/app.ts` 中：
```ts
const securityMiddleware = createSecurityMiddleware(config);
app.use("/api/*", securityMiddleware);
```
安全中间件在创建时将 `config.allowedOrigins` 读取并作为校验白名单。
`startServer` 自身具有 `EADDRINUSE` 端口自动顺延能力（若指定端口被占用，尝试 `port + 1`、`port + 2`...）。

如果 `bootstrap` 仅在启动前预设 `allowedOrigins = [http://127.0.0.1:${initialPort}]`，一旦发生端口回退（例如由 3000 回退到 3001），外部浏览器/客户端访问真实服务（3001 端口）并带上同源 Origin（`http://127.0.0.1:3001`）时，中间件持有的白名单仍停留在旧端口 3000，导致合法请求被自己的安全策略拦截并返回 403。

### 2. 解决方案与顺序保证
`bootstrap` 中采取了**双重确保真实端口匹配**的防御策略：
1. **启动前探测**：若传入端口为 0 或未指定，通过 `findAvailablePort()` 先探寻系统空闲端口作为基准起始端口；
2. **每次尝试对齐**：每次尝试绑定候选端口 `candidatePort` 时，动态使用当前端口构造 `allowedOrigins: [http://127.0.0.1:${candidatePort}, http://localhost:${candidatePort}]`；
3. **回退检测自愈**：如果 `startServer` 内部在并发竞争下发生了额外端口顺延并返回了不同于 `candidatePort` 的端口，`bootstrap` 会立即关闭该过渡实例，以该真实端口更新 `allowedOrigins` 后重新启动，确保运行中的应用其 `allowedOrigins` 100% 对应物理监听的真实端口。

## 三、端到端测试清单与运行证据

测试文件：`tests/runtime/integration/e2e.test.ts`（使用真实依赖，全量通过，无任何 fake）。

### 1. 覆盖用例清单
1. **健康检查与 Token 鉴权边界**：
   - 携带正确 Token（`X-AIRP-Token` 请求头）→ 200 `{ ok: true, airpHome, ... }`；
   - 携带正确 Token（`?token=` 查询参数）→ 200；
   - 无 Token → 403 Forbidden；
   - 错误 Token → 403 Forbidden。
2. **安全边界拦截**：
   - 非法 Origin（`Origin: http://evil.example`）→ 403 `Forbidden: origin not allowed`；
   - 非法 Host（`Host: evil.example`）→ 403 `Forbidden: invalid Host header`；
   - 合法 Origin（包含真实端口）→ 200。
3. **端口回退与 Origin 一致性验证**：
   - 原生 TCP 监听占用前置端口，`bootstrap` 自动顺延启动；
   - 发送带顺延后真实端口 Origin 的 `POST /api/cards`，成功返回 201，证明未被误杀。
4. **主链路端到端**：
   - `POST /api/cards` → 创建卡片并获取 `cardId`；
   - `POST /api/sessions` → 为该卡创建会话并获取 `sessionId`；
   - `POST /api/runs` → 启动生成 Run 并获取 `runId`；
   - `GET /api/runs/:runId/events` → 流式解析 SSE 事件帧，按 `run_delta` 累积文本直到收到 `end` 帧；
   - `GET /api/runs/:runId` → 查询最终 RunRecord，断言其 `text` 与累积 delta 完全一致。
5. **断线 reattach**：
   - 在流进行中接收 2 条以上事件后主动 abort 断开连接；
   - 使用 `?from=<已收到最大 seq>` 重新发起 SSE 订阅；
   - 补齐后续全部事件直至 `end` 帧；
   - 断言 reattach 收到的所有事件 `seq > maxFirstSeq`，且两批合并后 `seq` 单调连续递增，无任何重复与遗漏。
6. **持久化无损往返**：
   - `POST /api/cards` + `POST /api/sessions` + `appendFloor` 追加多楼层；
   - `GET /api/cards/:cardId/export` 导出 `ExportBundle`；
   - `POST /api/cards/import?newCardId=imported-card-test` 导入卡片；
   - 对新卡调用 `GET /api/sessions/:sessionId/tree?cardId=imported-card-test`；
   - 断言新卡的楼层树（`floors`、`activeBranchId`、`lastSeq`）与原卡完全一致。
7. **Run 取消语义**：
   - 启动慢速生成流，等待收到第一个 `run_delta`；
   - 调用 `POST /api/runs/:runId/cancel`；
   - 断言返回 `{ cancelled: true }`，Run 终态为 `cancelled`，且 `run.text` 非空（保留部分已生成文本）。
8. **资源释放**：
   - 调用 `server.close()`，验证旧端口连接拒绝；
   - 再次以相同端口调用 `bootstrap`，能够成功再次绑定该端口，证明资源彻底释放无泄露。

## 六、已知限制与阶段 3 注意事项

1. **模型适配层**：
   - 当前装配使用 `MockModelPort`（阶段 2 规约）。阶段 3 将接入真实的 `@earendil-works/pi-ai` 驱动真实 LLM 交互。
2. **Host 头与 Fetch 标准实现**：
   - Node 20+ 原生 `fetch` 实现会根据目标 URL 自动覆盖或规范化 `Host` 标头。在针对 `isAllowedHost` 的防御性校验测试中，需采用 `node:http` 原生请求以精确注入未被抹除的非法 Host 标头进行对抗测试。
3. **取消时序的节流依赖**：
   - 在真实取消测试中，RunManager 处于 150ms 节流或 4KB 缓冲中。测试取消保留文本时需确保模型流已输出至少一个字符并触发至少一次缓冲，避免在首字符输出前 cancel 导致已生成文本为空。
