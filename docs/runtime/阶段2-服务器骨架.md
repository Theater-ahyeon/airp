## 三、安全模型说明（三条防线各自的攻击面与对策）

```
[外部请求: 浏览器/外部脚本/本机进程]
               │
               ▼
┌────────────────────────────────────────────────────────┐
│ 第一道防线：Host 校验 (isAllowedHost)                   │
│ 攻击面：DNS Rebinding 攻击 (攻击者控制域名解析到本地回环) │
│ 对策：严格白名单只允许 127.0.0.1[:port] / localhost[:port]│
│       / [::1][:port]，非法 Host 直接拒绝 (403)。          │
└────────────────────────────────────────────────────────┘
               │ 通过
               ▼
┌────────────────────────────────────────────────────────┐
│ 第二道防线：Origin 校验 (isAllowedOrigin)               │
│ 攻击面：恶意外域跨域窃听与 CSRF/WebSocket/SSE 投毒        │
│ 对策：Origin 为空允许（同源/curl/本机 CLI）；           │
│       Origin 存在时必须严格匹配白名单，外域直接 403。   │
└────────────────────────────────────────────────────────┘
               │ 通过
               ▼
┌────────────────────────────────────────────────────────┐
│ 第三道防线：启动令牌校验 (extractToken + 时序安全比较)   │
│ 攻击面：本地未授权进程探测或时序侧信道猜测 Token          │
│ 对策：必须携带 32 字节高熵随机 Token；定长填充路径       │
│       crypto.timingSafeEqualString，绝不泄露长度信息。   │
└────────────────────────────────────────────────────────┘
               │ 通过
               ▼
         [业务路由处理]
```

1. **第一道防线：Host 标头校验（防 DNS Rebinding）**
   - **攻击面**：攻击者注册恶意域名 `evil.com`，将 DNS TTL 设为极短，初次解析到攻击者公网服务器下载恶意 JS，随后通过 DNS Rebinding 将 IP 解析为 `127.0.0.1`。浏览器由于同源策略认同为该域名同源，向 `127.0.0.1` 发送跨域请求，穿透浏览器的 SOP 限制。
   - **对策**：在中间件首要环节检查 HTTP `Host` 标头，强制校验只允许回环地址 `127.0.0.1:<port>`、`localhost:<port>` 及 IPv6 `[::1]:<port>`。一旦出现其他任何域名（如 `Host: evil.com`），即便 IP 路由到达本机，也立即返回 403，粉碎 DNS Rebinding 攻击链。

2. **第二道防线：Origin 来源标头校验（防恶意网页跨站渗透）**
   - **攻击面**：用户在同一浏览器中访问了第三方恶意网站，该网站脚本尝试向 `http://127.0.0.1:<port>` 发起 Fetch / XMLHttpRequest / EventSource 请求。
   - **对策**：根据浏览器规范，跨域请求必带 `Origin` 标头。当 `Origin` 存在时，服务端强制对比 `allowedOrigins` 白名单；非白名单域名立即拦截并返回 403。对于无 `Origin` 的请求（如命令行 `curl`、同源静态页面导航、自动化测试），则按设计予以放行。

3. **第三道防线：高熵启动令牌与定长时序安全比对（防未授权访问与时序侧信道）**
   - **攻击面**：本机其它低权限恶意进程扫描端口试图调用 AIRP 接口；或者攻击者通过精细测量逐字节字符串比对（Early-return）的响应时间差，逐步暴力枚举出合法 Token。
   - **对策**：服务启动时动态生成 32 字节密码学安全随机令牌（Base64URL 编码）。所有 `/api/*` 请求必须携带该 Token（支持 `X-AIRP-Token` 或 `?token=`）。比对采用 `timingSafeEqualString`：分配统一最大长度并做零填充对齐，不论输入长度是否一致，都恒定调用 `crypto.timingSafeEqual`，杜绝任何提前返回泄露长度与字符匹配进度的侧信道风险。

## 四、SSE reattach 时序说明与「SSE 只是视图」设计理由

### 1. Reattach 时序图

```
客户端 (Browser/Client)                            AIRP 服务端 (SSE + RunManager)
        │                                                         │
        │ 1. 建立初始连接: GET /api/runs/:id/events               │
        ├────────────────────────────────────────────────────────>│
        │                                                         │ 订阅事件流 (fromSeq = 0)
        │ 2. 接收事件帧                                           │
        │<────────────────────────────────────────────────────────┤ id: 1\nevent: run_delta\ndata: ...
        │<────────────────────────────────────────────────────────┤ id: 2\nevent: run_delta\ndata: ...
        │<────────────────────────────────────────────────────────┤ id: 3\nevent: run_delta\ndata: ...
        │                                                         │
     [网络中断 / 页面刷新]                                        │
        │                                                         │ 触发 AbortController -> unsubscribe()
        │                                                         │ 移除订阅，销毁定时器，防止内存泄漏
        │ 3. 重连请求: 带 Last-Event-ID: 3 或 ?from=3             │
        ├────────────────────────────────────────────────────────>│
        │                                                         │ 查询历史: EventLog/RunManager
        │                                                         │ 仅重放 seq > 3 的事件
        │ 4. 续传事件帧                                           │
        │<────────────────────────────────────────────────────────┤ id: 4\nevent: run_delta\ndata: ...
        │<────────────────────────────────────────────────────────┤ id: 5\nevent: run_delta\ndata: ...
        │                                                         │
        │ 5. 收到结束帧                                           │
        │<────────────────────────────────────────────────────────┤ event: end\ndata: <RunRecord>
        │                                                         │
        │ 6. 正常关闭连接                                         │
        ├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ >│
```

### 2. 「SSE 只是视图」核心设计理由
- **单一可信源原则（Single Source of Truth）**：AIRP 的持久化基础是 Append-only 的 `EventLog`（事件日志）。所有的 Run 文本增量、状态变更、分词统计在生成时就已按 seq 单调递增落盘到磁盘事件日志中。
- **服务端无状态恢复（Stateless Reconnection）**：如果将 SSE 流作为权威状态，服务端就必须在内存中维护每个客户端连接的复杂环形缓冲区（Ring Buffer）并管理其淘汰策略；一旦内存被回收或进程重启，客户端就永久丢失数据。将 SSE 定义为纯只读投影视图后，客户端断线重连只需携带已知的最后序列号 `fromSeq`，服务端直接从持久化底层按需重放 `seq > fromSeq` 的历史事件，随后无缝接入实时分发队列。
- **天然的高并发与断网容忍**：即便客户端断网 10 分钟，网络恢复后也只需一次标准的 HTTP SSE 重连即可完整恢复全部中间内容并同步至最终态，无需服务端常驻缓存负担。

## 五、凭据加密格式说明

凭据存储遵循 `<AIRP_HOME>` 隔离存储规则：

1. **主密钥文件**：`<AIRP_HOME>/.airp-key`
   - 首次初始化时由 `crypto.randomBytes(32)` 生成 32 字节强随机二进制密钥。
   - 文件写入模式采用 `mode: 0o600`（仅当前系统用户可读写）。

2. **加密凭据文件**：`<AIRP_HOME>/credentials.enc`
   - 采用标准 **AES-256-GCM** 认证加密。
   - 文件内容为 JSON 格式：
     ```json
     {
       "v": 1,
       "iv": "<12 字节 IV 的 Base64>",
       "tag": "<16 字节 GCM 认证标签的 Base64>",
       "data": "<AES-256-GCM 密文数据的 Base64>"
     }
     ```
   - **IV 防复用保证**：每次调用 `setSecret` 写入更新凭据时，必须重新调用 `crypto.randomBytes(12)` 独立生成全新初始化向量，绝对杜绝 GCM 模式下的 IV 复用风险。
   - **明文隔离**：加密对象为完整字典 `{ [secretName]: secretValue }`，无论是密钥的值还是密钥名称（如 `openai`、`sk-xxx`），均在加密前进入明文字符串，落盘时仅保存二进制密文的 Base64 编码，原始文件无任何可辨识文本。

## 七、契约缺口与已知限制

1. **`CharacterAttributes` 导出说明**：
   - `src/runtime/contracts.ts` 顶层 import 了 `CharacterAttributes`，但未显式 `export type { CharacterAttributes }`。在 `src/runtime/server/app.ts` 中遵照任务书要求，直接 `import type { CharacterAttributes } from "../../core/types/character.js"`，严格满足 TypeScript NodeNext 模式编译。
2. **OS Keychain 跨平台行为说明**：
   - 在 Windows 系统上（`process.platform === "win32"`），如任务书规范，不接入平台特定非标准命令行，如实声明 `backend: "encrypted-file"`，完全回退到标准的 AES-256-GCM 本地安全加密文件。
3. **SSE 客户端断开检测**：
   - 在 Hono 框架的 `streamSSE` 中，结合了 `stream.onAbort` 与 `c.req.raw.signal.addEventListener("abort")` 双重保障，确保 Node.js HTTP 连接被客户端重置或关闭时退订逻辑百分之百执行。
